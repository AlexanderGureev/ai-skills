# Шаблон и правила спеки

## Файл

- **Путь:** `spec/actual/NNN-название.md`.
- **Номер `NNN`:** три цифры — наибольший номер среди файлов `spec/actual/` и `spec/archive/` плюс один, взятый непосредственно перед созданием. Серия получает номера подряд в порядке выполнения.
- **Название:** латиница через дефис по сути задачи. В монорепе первое слово — приложение или пакет главного изменения (`025-web-api-keys.md`).
- **Объём:** одна спека — одна связная сессия реализации; независимые задачи — разные спеки. Деление крупной задачи на серию (со связью в «Зависимостях») — только по результатам, каждый из которых проверяется отдельно и оставляет проект рабочим; деление предлагается вопросом владельцу.

## Шаблон

Разделы по порядку; раздел без содержания не писать:

- NNN: <что из неё нужно>

## Исходные данные (ГГГГ-ММ-ДД)

## Правила текста

- **Уровень спеки.** Фиксировать цель, поведение, инварианты, внешние контракты (полями и правилами, а не кодом библиотек и внутренними типами), хранимые форматы, границы модулей и риски; внутреннее устройство и способ правки существующего кода внутри одного процесса выбирает `/impl` по `AGENTS.md` и `principles.md`. Тест на лишнюю деталь: если другая сигнатура, имя символа или перестройка внутренней структуры сохраняют поведение, инварианты и границы — убрать или переписать инвариантом.
  - *Слишком детально:* «Добавить `buildExportModel()` и проп `onlyDated` в `ExportPopover`, защитить клик через `pendingRef`».
  - *Как нужно:* «Подготовка раскладки экспорта не зависит от DOM/Canvas и проверяется в Node; на время операции повторный запуск заблокирован».
- **Исходные данные и ссылки.** Записывать только факты и ограничения, без которых можно принять неверное решение или упустить риск; карту изменяемых файлов и устройство существующих функций не конспектировать — `/impl` прочитает их в коде. Ссылаться путями файлов без хрупких номеров строк (`file:line` остаются в раунде). Один пункт — одна мысль, без вложенных скобок, длинных абзацев и повтора одних и тех же списков между разделами.
- **Критерии готовности.** Формулировать через наблюдаемое поведение, ключевые сценарии и риски — кратко, без пересказа каждого подпункта требований и без привязки к внутренним деталям реализации. Одна проверка может закрывать несколько требований; указывать только реально проверяемые. Общую проверку проекта из `AGENTS.md` отдельным критерием не дублировать — её запускает `/impl` последней, и она сама закрывает сборку, типы и линт.
- **Самостоятельная проверка и редкий `[владелец]`.** Агент сам проверяет поведение и UI (сценарий в браузере, отсутствие ошибок консоли, визуальный осмотр скриншотов при изменении вида). Пометку `[владелец]` ставить только для проверки, которую агент физически не может выполнить (чужое устройство, внешнее приложение, прод-стенд), либо когда владелец в `/spec` явно попросил ручную визуальную/вкусовую приёмку; не смешивать `[владелец]` с проверками агента в одном критерии.
- **Чистота текста.** Удалять текст, не задающий действие, ограничение или проверку, и ссылки на контекст обсуждения (скриншоты, файлы из чата, временные аудит-логи).
- После записи проверить спеку самому по `../review/spec-checklist.md`; пробелы исправить до этапа 3.
