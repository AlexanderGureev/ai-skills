# Шаблон и правила спеки

## Файл

- **Путь:** `spec/actual/NNN-название.md`.
- **Номер `NNN`:** три цифры — наибольший номер среди файлов `spec/actual/` и `spec/archive/` плюс один, взятый непосредственно перед созданием. Серия получает номера подряд в порядке выполнения.
- **Название:** латиница через дефис по сути задачи. В монорепе первое слово — приложение или пакет главного изменения (`025-web-api-keys.md`).
- **Объём:** одна спека — одна связная сессия реализации; независимые задачи — разные спеки. Деление крупной задачи на серию (со связью в «Зависимостях») — только по результатам, каждый из которых проверяется отдельно и оставляет проект рабочим; деление предлагается вопросом владельцу.

## Правила текста

- **Уровень спеки.** Фиксировать цель, поведение, инварианты, внешние контракты, хранимые форматы, границы модулей и риски; внутреннее устройство кода внутри одного процесса выбирает `/impl` по `AGENTS.md` и `principles.md`. Тест на лишнюю деталь: если переименование символа или иная внутренняя структура кода сохраняют поведение, инварианты и границы — убрать или переписать инвариантом.
  - *Слишком детально:* «Добавить `buildExportModel()` и проп `onlyDated` в `ExportPopover`, защитить клик через `pendingRef`».
  - *Как нужно:* «Подготовка раскладки экспорта не зависит от DOM/Canvas и проверяется в Node; на время операции повторный запуск заблокирован».
- **Исходные данные и ссылки.** Указывать только факты, ограничения и существующие точки входа, от которых зависит решение или риск; перечни всех затрагиваемых символов ради полноты не писать. Писать коротко: один пункт — одна мысль, без вложенных скобок и длинных абзацев.
- **Критерии готовности.** Формулировать через проверяемое поведение и риски, без привязки к выдуманным внутренним именам и новым тестовым файлам. Одна проверка может закрывать несколько требований; указывать только реально проверяемые. Общую проверку проекта из `AGENTS.md` отдельным критерием не дублировать — её запускает `/impl` последней, и она сама закрывает сборку, типы и линт.
- **Самостоятельная проверка и редкий `[владелец]`.** Агент сам проверяет поведение и UI (сценарий в браузере, отсутствие ошибок консоли, визуальный осмотр скриншотов при изменении вида). Пометку `[владелец]` ставить только для проверки, которую агент физически не может выполнить (чужое устройство, внешнее приложение, прод-стенд), либо когда владелец в `/spec` явно попросил ручную визуальную/вкусовую приёмку; не смешивать `[владелец]` с проверками агента в одном критерии.
- **Чистота текста.** Удалять текст, не задающий действие, ограничение или проверку, и ссылки на контекст обсуждения (скриншоты, файлы из чата).
- После записи проверить спеку самому по `../review/spec-checklist.md`; пробелы исправить до этапа 3.
