# Ревью

Цель: найти (1) ошибки корректности; (2) изменения, после которых следующая задача того же рода требует больше изменений. Стиль и форматирование не проверяются.

Перед работой прочитать `principles.md` (рядом с этим `SKILL.md`) и разделы `AGENTS.md` корня и затронутых модулей.

Объект:

- без аргумента → `staged`, а если `staged` пуст — всё незакоммиченное (`HEAD` и новые файлы вне git);
- диапазон git → его изменения;
- файл, каталог или весь проект → весь код по пути (целиком считается задачей; спеки нет);
- номер или путь спеки → эта спека;
- спека + диапазон git или путь → код из диапазона/пути против этой спеки.

Маршрут: в объекте только спеки → прочитать `spec-checklist.md` (рядом с этим `SKILL.md`) и проверить по нему. Иначе → «Ревью кода». Спека и лог для «Ревью кода»: переданные вызывающим или в аргументе; иначе лог из изменений (для незакоммиченного — включая неотслеживаемые файлы из `git status`) и спека с тем же номером; лога нет → спеки нет.

## Ревью кода

1. **Контекст.** Прочитать спеку и лог (цель, решения, отступления; строка «Решений» с собственной датой главнее меняемого требования). Спеки нет → цель из запроса или сообщений коммитов.
2. **Сигналы.** Выполнить `node "<каталог этого навыка>/signals.mjs" [диапазон] [-- пути]` для объекта. Каждый сигнал является вопросом, на который нужен ответ по коду. Пропустить, если объект — файл/каталог, нет Node или нет git.
3. **Полнота.** Для каждого требования и критерия спеки указать место реализации (`file:line`) и чем проверено. Незаписанное в логе отступление — находка.
4. **Новое.** Для новых модулей, экспортов, полей, опций и параметров проверить владельца, потребителя (принцип 6) и единственный источник данных (принцип 3). Для объекта-пути — по модулям и поиску usages.
5. **Проход.** Читать по слоям: домен → контракты и форматы → внешние слои (UI, API, сервер) → инструменты и тесты → документация. Искать «Тихие ошибки» и нарушения принципов 1–12, внесённые задачей. Если задача добавила сущность существующего или подтверждённого рода (принцип 7), перечислить файлы, которые изменятся при добавлении ещё одной: больше одного места — находка.
6. **Подтверждение.** Без подтверждения находки нет:
   - ошибка поведения: цепочка `file:line` или короткая проба во временной папке (если сборка не позволяет — временный тест в дереве, удалить после проверки; полные наборы тестов не запускать);
   - структурная: `file:line` и поиск по usages;
   - на диапазоне коммитов сверять с текущим кодом (исправленное позже не находка).
7. **Ошибка в спеке.** Записать находкой с поправкой спеки, а не с обходом в коде. Конфликт цели и спеки — находка в «Существенно» с вариантами и ценой для владельца.
8. **Отчёт** по шаблону ниже. Код не менять до просьбы владельца.

### Тихие ошибки

1. **Состояние вне источника истины:** кэш, флаг, счётчик или производное переживает событие, сохранение, перезагрузку или перезапуск; производное пересчитывается позже события.
2. **Lifecycle:** ресурс, подписка, таймер или запрос без владельца и отмены; освобождение раньше последнего потребителя; сбой повторной инициализации. (Объекту на весь срок жизни приложения очистка не нужна.)
3. **Граничные входы:** пусто, ноль, отрицательное, переполнение, повтор, параллельный вызов, действие во время другого, неизвестный исход внешнего вызова (таймаут или обрыв после выполнения).
4. **Расхождение входа и выхода:** код производит значение, которое отклоняет его же проверка; проверка после побочного эффекта.
5. **Защищённый контракт:** контракт, защищённый разделом «Статус» `AGENTS.md`, изменён без миграции.
6. **Ошибки и безопасность:** проглоченная ошибка; секрет в логе или ответе; проверка прав не у модуля-владельца; непроверенный внешний ввод в запросе, команде или пути.

## Предложения

- Исправление, не устраняющее ошибку, не добавляет больше строк и понятий, чем удаляет.
- Не предлагать: абстракцию для кода, совпадающего лишь записью (принципы 3, 6); флаг в общем пути вместо безопасного поведения по умолчанию.
- Код, бывший до задачи, относить в «Не трогаю», кроме случаев, когда он мешает чистой реализации задачи.

## Отчёт

«Критично»: ошибки корректности (для спеки: блокеры, противоречия, пробелы против цели). «Существенно»: рост сложности и нарушения принципов. Нумерация сквозная; пустой раздел: «нет». Для спеки вместо `file:line` указать раздел и пункт, строку `Проверено` пропустить.

```
Вердикт: <полнота по задаче; есть ли критичное; растёт ли сложность; 1–2 фразы>

Критично
1. <file:line>; <сценарий и последствие>; <подтверждение>; <исправление>

Существенно
2. <принцип>; <file:line>; <почему следующая задача станет дороже>; <исправление, что удалится>

Проверено: <слой: что проверено>; …
Не трогаю: <что: решение спеки без ошибки | цена не подтверждена | было до задачи>
```

## Исправление

Выполнять для находок, которые назвал владелец, или по вызову из `impl`. Находку ревью спеки исправить правкой текста спеки; шаги ниже — для кода:

1. Ошибка поведения: проба/сценарий падает → правка → проходит. Структурная: правка → поиск по старым usages.
2. Обновить затронутые `README`, `docs`, комментарии и заполненную «Карту проекта» `AGENTS.md` (принцип 12); остальные разделы `AGENTS.md` без просьбы владельца или требования спеки не менять.
3. Только при автономном `/review` (по команде владельца): если правка меняет решение спеки, дописать строкой в «Решения» спеки `- <выбор>; владелец, ГГГГ-ММ-ДД; <почему>`, остальной текст спеки не править; выполнить проверки из «Проверки изменений» `AGENTS.md`. (В `impl` ошибки решений спеки не правятся, а идут в вопросы; итоговые проверки идут отдельным этапом.)
4. Чужие изменения в рабочем дереве не трогать; `staged` не менять.
5. Если шаг «Сигналы» выполнялся, повторить `node "<каталог этого навыка>/signals.mjs" HEAD -- <изменённые файлы>`; пройти свой дифф по `principles.md`, прежде всего по принципу 6.
