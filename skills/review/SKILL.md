# Ревью

Цель: найти (1) ошибки корректности; (2) изменения, после которых следующая задача того же рода требует больше
изменений. Стиль и форматирование не проверяются.

Объект:

- без аргумента → staged, а если staged пуст, всё незакоммиченное (`HEAD`);
- диапазон git → его изменения;
- файл, каталог или весь проект → весь код по пути, он целиком считается задачей; спеки нет;
- номер или путь спеки → эта спека.

В объекте только спеки → «Ревью спеки»; иначе → «Ревью кода». Спека и лог задачи для «Ревью кода»: лог из
изменений и спека с тем же номером; лога в изменениях нет → спеки нет.

Правила: принципы ниже и разделы AGENTS.md корня и затронутых модулей, которые касаются объекта. Правило AGENTS.md
главнее правила навыка.

## Принципы

**Главный принцип: сложность растёт только ради текущей задачи.**

- Сложность: понятия и связи, которые нужно удержать, чтобы безопасно изменить код. Это модули, абстракции, типы,
  опции, флаги, параметры, зависимости, пути выполнения, связи через границу модулей, места, где записано одно
  правило.
- Каждый добавленный элемент из этого списка оправдан текущей задачей. Удалённый элемент считается выигрышем.
- Критерий: после задачи следующая задача того же рода требует не больше изменений, чем до неё.

1. **Порядок выбора решения.** Взять первый вариант, который полностью решает задачу:
   1. не делать: требование не нужно или его закрывает продуктовое ограничение (решает владелец);
   2. уже есть в проекте: использовать так же, как соседний код;
   3. платформа или стандартная библиотека;
   4. установленная зависимость;
   5. новый код минимального объёма у модуля-владельца.

   Новая зависимость допустима, только если заменяет больше кода, чем добавляет, и её принял владелец. При равном
   объёме выбрать вариант, корректный на граничных входах, затем читаемый без расшифровки.
2. **Полная правка.** До правки найти все места, куда она должна дойти: вызовы, тесты, фикстуры, конфигурация,
   экспорты, документация. Решение минимально; правка доведена во всех найденных местах.
   - Правка общей функции: пройти все usages; изменение результата для других потребителей, которого задача не
     требует, изолировать; требуемое записать в лог как решение.
3. **Модуль-владелец.** У каждого состояния, данных, ресурса, правила и lifecycle один модуль-владелец (единственный
   модуль, который его создаёт и меняет) и один источник истины.
   - Модуль для нового кода выбирается по источнику данных, частоте обновления и сроку жизни, а не по сходству
     результата. Общий код сущностей разных модулей выносится в нейтральный модуль, а сущности остаются
     равноправными потребителями.
   - Правило домена (предикат, формула, предел, общая константа) записано одной функцией или константой у
     модуля-владельца, общие данные (конфиг, фикстура) одним файлом. То же правило в другом модуле считается дублем,
     даже в одну строку. Код, совпадающий только записью при разном смысле (меняется независимо), дублем не
     считается. Производное считается один раз и передаётся.
   - К одному состоянию, формату или действию ведёт один путь через модуль-владелец.
   - Признаки нового, прицепленного к похожему модулю: оговорка «кроме…» в описании модуля; поля и входы, нужные
     только новой части; один метод смешивает разные частоты обновления; правило домена в слое представления.
   - Признаки чужого домена ради переиспользования: одна сущность наследует другую; данные одной сущности в
     контейнере другой; проверки типа и пустые значения компенсируют несовпадение.
   - Признаки дубля: одинаковые проверка принадлежности, признак вида, формула или предел в двух модулях (у
     производителя и у проверяющего); одинаковые копии данных, конфигов, фикстур.
   - Признаки второго пути: повторный вход в начало действия; запись одного состояния из двух мест; сборка данных в
     обход модуля-владельца формата; повторная дорогая работа (разбор, хеш, нормализация).
4. **Явные границы.**
   - Модули связаны узким API; зависимости и порядок вызовов видны в точке сборки.
   - Запрещено: собственное глобальное изменяемое состояние, скрытая регистрация, доступ к внутренностям чужого
     модуля, циклические импорты.
   - Событие только для независимых подписчиков; иначе прямой вызов.
   - Механизм фреймворка, принятый в проекте (DI, декораторы маршрутов, store), не нарушение. Собственный скрытый
     механизм поверх него нарушение.
   - Границу, которую можно закрепить типом, входом модуля или линтом, закреплять.
   - Отладочные сценарии, флаги и инструменты лежат в отдельном модуле, который отключается целиком, а не в ядре
     или продуктовом модуле.
5. **Устройство соседей.** Новое повторяет слои, интерфейсы и конвенции соседа того же рода. Своя конвенция только с
   записанной причиной.
6. **Только существующее.**
   - У каждой абстракции, опции, поля, параметра, экспорта и ветки есть потребитель: код, который сегодня их читает
     или вызывает.
   - Абстракция вводится, только если убирает существующее дублирование.
   - Значение передаётся в той форме, которую уже даёт платформа или модуль-владелец, без обёрток и преобразований.
   - Исключения: (а) значение, которое будут подбирать, оформляется именованной константой у модуля-владельца;
     (б) под ближайшую сущность того же рода, подтверждённую владельцем, сразу задаются границы и типы, без опций и
     флагов.
   - Признаки: ветка или опция под отсутствующий сценарий; необязательный параметр, который передают все; экспорт
     или поле, которые никто не читает. Исправление: удалить; параметр, который передают все, сделать обязательным.
7. **Вторая сущность.** Когда сущность такого рода (страница, провайдер, тип объекта, домен API) в проекте уже есть
   или следующую подтвердил владелец, новая добавляется данными или правкой у одного модуля-владельца. Нарушение:
   копии блоков или ветки по типу в нескольких местах. К первой сущности без подтверждённой следующей принцип не
   применяется.
8. **Причина, а не симптом.**
   - Ошибка исправляется один раз в общем коде у модуля-владельца, после поиска всех вызовов.
   - Запрещён костыль, который маскирует ошибку: таймер, повтор, порог, подобранная константа или коэффициент,
     пустой обработчик, молчаливый fallback, значение по умолчанию вместо обязательного.
   - Если причину нельзя устранить в задаче: вопрос владельцу с рекомендацией ввести продуктовое ограничение,
     закрывающее весь род таких ошибок.
9. **Явный контракт.** Контракт между модулями и функциями выражен типом или схемой.
   - Взаимоисключающие состояния выражены типом без невозможных сочетаний.
   - Внешние данные проверяются типом или схемой один раз на входе; внутренний код опирается на инварианты и не
     перепроверяет их.
   - Признаки: связь по позиции в массиве; два необязательных поля вместо union; особое значение (`-1`, `""`,
     `null`) как сигнал; проверка типа внутри функции; данные через скрытый модульный кэш.
10. **Замена целиком.**
    - Старая модель удаляется в той же задаче: ветки, типы, адаптеры, тесты, настройки, тексты. Признак остатка:
      поиск по старым именам находит код, тесты, настройки, комментарии или docs.
    - Совместимость и миграции только если их требует раздел «Статус» AGENTS.md.
    - Перенос и слияние кода сохраняют проверки, обработку ошибок, приоритет отказов и порядок побочных эффектов;
      перенесённый тест проверяет не меньше прежнего.
11. **Сложность за цифру.** Код ради производительности только с выигрышем, подтверждённым замером; цифра записана в
    лог.
12. **Правдивые тексты и тесты.**
    - README и docs описывают текущее состояние, без истории. Меняются, только если без правки они неверны или не
      упоминают добавленные задачей поведение, команду, контракт или модуль.
    - Комментарий только о неочевидном: причина решения, обход ошибки среды, требование порядка, единицы. Без
      номеров спек и истории правок.
    - Признаки: README, docs или комментарий описывают старое поведение или другого модуля-владельца; утверждение
      теста истинно всегда. Исправление: привести к коду.

**Не упрощается:** проверка на границе доверия; обработка ошибок, защищающая данные от потери; безопасность и доступ;
доступность интерфейса; то, что владелец явно потребовал.

## Ревью кода

1. **Контекст.** Спека и лог задачи: переданные вызывающим, иначе из объекта. Прочитать цель, решения, отступления;
   строка «Решений» с собственной датой главнее требования, которое она меняет. Спеки нет: цель взять из запроса или
   сообщений коммитов, шаг 3 выполнить по пунктам цели.
2. **Сигналы.** Выполнить `node "${CLAUDE_SKILL_DIR}/signals.mjs" [диапазон] [-- пути]` для того же объекта; скрипт
   лежит рядом с этим файлом. Каждый сигнал является вопросом, на который нужно ответить по коду. Объект является
   файлом или каталогом, или нет Node: шаг пропустить.
3. **Полнота.** Для каждого требования и критерия готовности спеки указать, где реализовано (`file:line`) и чем
   проверено. Отступление от спеки без записи в логе является находкой.
4. **Новое.** Для каждого нового модуля, экспорта, поля, опции и параметра указать модуль-владелец, потребителя и
   источник данных. Нет потребителя (принцип 6) или два источника (принцип 3): находка. Объект-путь: по модулям;
   экспорты без потребителя найти поиском по usages.
5. **Проход.** Читать по слоям: домен → форматы данных и контракты → внешние слои (UI, API, сервер) → инструменты и
   тесты → документация. Тесты читать по требованиям спеки, данные и сгенерированное по сигналам. В каждом слое
   искать «Тихие ошибки» и нарушения принципов 1–12. Нарушение принципа является находкой, только если его внесла
   задача.
6. **Вторая сущность.** Если задача добавила сущность (страницу, провайдер, тип, обработчик) рода, который в проекте
   уже был или следующую сущность которого подтвердил владелец, перечислить файлы, которые изменятся при добавлении
   ещё одной. Больше одного места: находка по принципу 7. Иначе шаг пропустить.
7. **Подтверждение.** Без подтверждения находки нет.
   - Ошибка поведения: сценарий по коду (цепочка `file:line`) или проба.
   - Структурная: `file:line` и поиск по usages.
   - Проба: короткий скрипт или тест во временной папке. Если сборка не позволяет, временный тест в дереве, удалить
     после проверки. Полные наборы тестов не запускать.
   - Диапазон коммитов: спеку брать на конце диапазона, находку сверить с текущим кодом. Исправленное позже не
     находка.
8. **Ошибка в спеке.** Ошибку, заложенную в решении спеки, записать находкой с поправкой спеки, а не с обходом в коде.
   Конфликт цели и спеки: находка в «Существенно» с вариантами и ценой для владельца.
9. **Отчёт** по разделу «Отчёт». Код не менять до просьбы владельца.

### Тихие ошибки

1. Состояние вне источника истины: кэш, флаг, счётчик или производное значение переживает событие, сохранение,
   перезагрузку или перезапуск; производное пересчитывается позже события.
2. Lifecycle: ресурс, подписка, таймер или запрос без модуля-владельца и без отмены; освобождение раньше последнего
   потребителя; повторная инициализация и её сбой. Объекту на весь срок жизни приложения очистка не нужна.
3. Граничные входы: пусто, ноль, отрицательное, переполнение, повтор, параллельный вызов, действие во время другого,
   неизвестный исход внешнего вызова (таймаут или обрыв после выполнения).
4. Вход и выход расходятся: код производит значение, которое отклоняет его же проверка; проверка стоит после
   побочного эффекта.
5. Контракт, защищённый разделом «Статус» AGENTS.md (API, схема, формат данных), изменён без миграции.
6. Ошибки и доступ: проглоченная ошибка; секрет в логе или ответе; проверка прав не в модуле-владельце.

## Ревью спеки

Пройти чек-лист. Невыполненный пункт является находкой: место в спеке, сценарий, исправление.

- [ ] Цель достижима требованиями спеки.
- [ ] Подход выбран по принципу 1; упрощение требованием (продуктовое ограничение, меньше вариантов и сочетаний)
      рассмотрено.
- [ ] У каждого нового правила, модуля и данных есть модуль-владелец, выбранный по данным, а не по сходству
      (принцип 3).
- [ ] Если сущность такого рода уже есть или следующую подтвердил владелец, новая добавляется в одном месте
      (принцип 7); нет опций и веток под отсутствующие сценарии (принцип 6).
- [ ] Решение не нарушает остальных принципов: нет костыля, дубля правила, второго пути, скрытой связи через
      границу модулей; код, мешающий реализации, перечислен в «Код, мешающий реализации».
- [ ] Для каждого рода кода, который задача добавляет или меняет, риск закрыт требованием или критерием готовности:
      состояние и данные → согласованность; хранимые данные и внешний контракт → совместимость и миграции (раздел
      «Статус» AGENTS.md); ресурсы, подписки, таймеры → lifecycle; сетевые вызовы → отказы и таймауты; доступ и
      секреты → безопасность; новый путь отказа или фоновый процесс → наблюдаемость (что пишется в лог и метрики,
      без секретов и персональных данных); горячий путь → производительность; интерфейс → внешний вид. Риски кода,
      который задача не меняет, не проверяются.
- [ ] «Что удаляется» перечисляет всё, что заменяет спека: код, ветки, тесты, настройки, тексты.
- [ ] Документы, которые описывают изменяемое поведение (docs, навык или спека проекта, описание внешней системы),
      обновляются требованием, и «Границы и запреты» их правку не запрещают; поиск остатков старой модели в критериях
      охватывает код, docs и спеки `spec/actual/`, кроме текущей; `spec/archive/` не проверяется.
- [ ] Разделы спеки не противоречат друг другу и AGENTS.md.
- [ ] Каждое требование проверяемо и закрыто критерием готовности со способом проверки; способ выбран по риску из
      «Проверки изменений» AGENTS.md; каждая долгая проверка (полный набор тестов, e2e, сборка, замер) указана в
      одном критерии.
- [ ] Нет жёсткого порога для шумной метрики (время, кадры, память), который вынудит костыль.
- [ ] Пути и символы из «Исходных данных» и «Кода, мешающего реализации» существуют в коде.

## Предложения

Правила для исправлений, которые предлагает отчёт:

- Сравнить, что исправление удаляет и что добавляет. Исправление, которое не устраняет ошибку, не добавляет больше
  строк и понятий, чем удаляет.
- Не предлагать: общий класс, интерфейс, стратегию или хелпер для кода, совпадающего только записью (принцип 3);
  флаг в общем пути вместо безопасного поведения по умолчанию.
- Одно правило для всех сущностей рода предпочтительнее веток по типу.
- Код, который был до задачи, относится к «Не трогаю», кроме кода, мешающего реализации задачи.

## Отчёт

По шаблону. «Критично»: ошибки корректности. «Существенно»: рост сложности и нарушения принципов. Нумерация находок
сквозная; пустой раздел: «нет». В находке по спеке вместо `file:line` указать раздел и пункт спеки.

```
Вердикт: <полнота по задаче; есть ли критичное; растёт ли сложность; 1–2 фразы>

Критично
1. <file:line>; <сценарий и последствие>; <подтверждение>; <исправление>

Существенно
2. <принцип>; <file:line>; <почему следующая задача станет дороже>; <исправление, что удалится>

Проверено: <слой: что проверено>; …
```
