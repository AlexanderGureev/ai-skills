# Реализация спеки

Результат: спека реализована целиком; каждый критерий готовности доказан в логе; спека и лог перенесены или
оставлены по разделу «Завершение».

Правила полноты:

- Объём спеки не сокращать; части не откладывать; реализацию не заменять планом или описанием.
- Если требование заблокировано (строки 2–3 «Спеки и реальности»), выполнить остальное, а заблокированное записать в
  «Не сделано, риски, вопросы владельцу» с причиной.
- Один запуск выполняет одну спеку. Несколько спек в запросе: выполнить первую в порядке «Зависимостей»; остальные
  назвать в отчёте строкой «Дальше: <номера>, после коммита».

Порядок: Старт → Реализация → Ревью → Итоговые проверки → Завершение.

## Старт

1. Найти спеку по номеру или пути в `spec/actual/`. Спека в `spec/archive/` и её файл не закоммичен (есть в
   `git status`): вернуть спеку и лог в `spec/actual/`, ссылки на `spec/archive/NNN-` заменить обратно, продолжить.
   Спека в `spec/archive/` закоммичена: сообщить владельцу, что доработка оформляется новой спекой, и остановиться.
   Спеки нет: сообщить владельцу и остановиться. Спека из «Зависимостей» не реализована: вопрос владельцу до начала.
   Зависимость реализована, если она в `spec/archive/` без строки «Отклонено» в логе или в «Готовности» её лога
   недоказаны только критерии «владелец».
2. Прочитать: спеку; «Решения» спек из её «Зависимостей» и «Отступления и находки» их логов; раздел «Принципы»
   навыка `review` (`${CLAUDE_SKILL_DIR}/../review/SKILL.md`, где `${CLAUDE_SKILL_DIR}` означает каталог этого
   навыка); AGENTS.md корня и затронутых модулей; документацию затронутых модулей. Раздел AGENTS.md, нужный для
   работы, пуст или заготовка: вопрос владельцу до начала.
3. Определить состояние по логу `spec/actual/NNN-название-log.md`; выбрать первую подходящую строку сверху:

   | Состояние | Продолжить с |
   | --- | --- |
   | владелец сказал «в архив» или отклонил | «Завершение» |
   | владелец ответил на вопрос из «Не сделано, риски, вопросы владельцу» или дал замечание к результату | ответ или замечание записать строкой в «Решения» спеки; из лога удалить раздел «Ревью», итог общей проверки проекта в «Готовности» и отвеченный пункт из «Не сделано, риски, вопросы владельцу»; «Реализация», этап по этой строке |
   | в «Готовности» есть успешный итог общей проверки проекта | «Завершение» |
   | раздел «Ревью» есть | разобрать находки без итога; «Итоговые проверки» |
   | все этапы есть в «Что сделано» | «Ревью» |
   | лог есть | сверить «Что сделано» с `git status` и диффом; изменения вне «Что сделано» в файлах первого несделанного этапа считать своими и доделать этап; остальные изменения чужие |
   | лога нет | в дереве есть незакоммиченные изменения вне `spec/`: вопрос владельцу (закоммитить или считать чужими) и ждать ответа; затем создать лог по шаблону; «Реализация», первый этап |

   Сделанное не переделывать и не откатывать.
4. Сверить «Исходные данные» спеки с кодом. Расхождение, меняющее решение спеки, обработать по таблице «Спека и
   реальность».

## Правила на всё время работы

- Менять только то, что требует спека. Посторонний рефакторинг не делать; замеченный чужой долг записать в
  «Отступления и находки».
- Чужие правки (изменения рабочего дерева вне «Что сделано» и незавершённого этапа) не трогать.
- Не коммитить; не менять staged без просьбы владельца.
- Спеку не править. Единственная правка: ответ или замечание владельца в этой сессии, строка в «Решения» вида
  `- <выбор>; владелец, ГГГГ-ММ-ДД; <почему>`; она главнее требования, которое меняет.

## Реализация

1. Этапы берутся из «Порядка работы» спеки. Если его нет: «Код, мешающий реализации»; затем пункты верхнего уровня
   «Требований» по порядку; последним «Что удаляется». Строки «Решений», добавленные владельцем при доработке, дают
   этапы в конце.
2. До правки каждого этапа найти все места, куда она должна дойти (принцип 2 `review`).
3. После каждого этапа записать в «Что сделано» этап, файлы, символы.
4. Проверки:
   - после каждого этапа: проверки изменённых файлов из «Проверки изменений» AGENTS.md, кроме долгих;
   - долгие проверки (полный набор тестов, e2e, сборка, замер) только в «Итоговых проверках»;
   - проверку повторять только после изменения кода;
   - упавшая проверка: найти причину и исправить; перезапуск без правки запрещён;
   - платные операции (платный API, облачные ресурсы) в пределах из спеки или сообщения владельца; предела нет или
     он исчерпан: спросить до запуска.
5. Если изменилось поведение или контракт, обновить README, docs, комментарии и «Карту проекта» AGENTS.md, если она
   заполнена, в том же этапе. Остальные разделы AGENTS.md без просьбы владельца не менять.

### Спека и реальность

| Ситуация | Действие |
| --- | --- |
| требование невыполнимо как написано; цель достижима иначе, и обход не меняет поведение для пользователя, внешний контракт (то, что читают другой процесс, другой проект или мониторинг), хранимый формат данных, зависимости или строку «Решений» с автором «владелец»; типы и сигнатуры между модулями одного процесса такой обход может менять | сделать иначе; запись в «Отступления и находки» с причиной |
| нужно решение владельца: обход меняет поведение для пользователя, внешний контракт, хранимый формат данных, зависимости или строку «Решений» с автором «владелец» | выполнить остальное; вопрос с рекомендацией в «Не сделано, риски, вопросы владельцу» |
| требование противоречит цели спеки или AGENTS.md | выполнить остальное; вопрос с рекомендацией в «Не сделано, риски, вопросы владельцу» |
| критерий готовности не выполняется | найти причину и исправить; критерий не ослаблять, проверку не подгонять |

## Лог

Шаблон:

```
# NNN. Название: лог

ГГГГ-ММ-ДД

## Что сделано
### Этап N. <название>
- `<файл>`: <символ>; <что сделано>

## Отступления и находки
- <что>; <почему>; <чем заменено | доказательство>

## Готовность
| Критерий готовности | Доказательство |
| --- | --- |
| 1. <критерий> | <команда и итог вывода | сценарий | скриншот | ждёт владельца: как проверить> |

Стенд и пробы: <одна строка>

## Ревью
- <находка>: исправлено | отклонено, <причина> | передано в вопросы

## Не сделано, риски, вопросы владельцу
- <пункт>
```

Правила лога:

- В логе записываются решения и доказательства, а не ход работы.
- Критерий без доказательства в «Готовности» не выполнен.
- Раздел «Ревью» пишется всегда; нет находок: «находок нет». Остальные пустые разделы не писать.
- Правки при разборе ревью и в итоговых проверках записываются в «Что сделано» этапом «Исправления».

## Ревью

1. Когда: после всех этапов, до «Итоговых проверок».
2. Запустить подагент: обычный, не fork, без контекста сессии. Передать: пути спеки и лога; список файлов задачи с
   пометкой новых; путь `${CLAUDE_SKILL_DIR}/../review/SKILL.md`; задание:
   - ревью по навыку `review` против спеки: полнота по каждому требованию, затем «Ревью кода»;
   - дифф: `git diff HEAD -- <файлы задачи>`, новые файлы читать целиком; сигналы:
     `node "${CLAUDE_SKILL_DIR}/../review/signals.mjs" HEAD -- <файлы задачи>`; остальные изменения в дереве
     считаются чужими;
   - находка только подтверждённая; стиль не проверять; непрогнанные итоговые проверки не находка; файлы не менять.
3. Ответ сразу записать в «Ревью» списком находок; итог каждой дописать при разборе. Для каждой находки выбрать
   первую подходящую строку сверху:

   | Находка | Действие |
   | --- | --- |
   | ошибка в решении спеки | вопрос с рекомендацией в «Не сделано, риски, вопросы владельцу»; в «Ревью»: «передано в вопросы» |
   | опровергнута по коду (`file:line`) или противоречит спеке или AGENTS.md | в «Ревью»: «отклонено, <причина>» |
   | остальные | исправить по разделу «Исправление» навыка `review`; в «Ревью»: «исправлено» |

4. Один подагент на проход «Ревью»: исправленное по находкам перепроверить самому, повторный подагент ради
   исправлений не запускать.

## Итоговые проверки

1. После исправлений по ревью выполнить проверки из «Критериев готовности», затем общую проверку проекта из «Проверки
   изменений» AGENTS.md последней.
2. Упавшая проверка: исправить причину, повторить её и общую проверку проекта. Причина не устранена: критерий в «Не
   сделано, риски, вопросы владельцу» с выводом проверки.
3. Итог каждой проверки записать в таблицу «Готовность».

## Завершение

Выбрать первую подходящую строку сверху:

| Условие | Действие |
| --- | --- |
| владелец отклонил | откатить свои изменения задачи, не трогая чужих правок; в лог: «Отклонено: <причина>»; перенести спеку и лог в архив, как в третьей строке |
| владелец принял («в архив», в любой сессии) | в «Доказательство» критериев «владелец»: «принято владельцем ГГГГ-ММ-ДД»; перенести, как в третьей строке |
| все требования выполнены, все критерии доказаны | `mv` спеки и лога в `spec/archive/`; ссылки на `spec/actual/NNN-` заменить на `spec/archive/NNN-` |
| есть невыполненное требование или недоказанный критерий без пометки «владелец» | оставить в `spec/actual/` |
| недоказаны только критерии «владелец» | оставить в `spec/actual/`; в отчёте указать, что и как проверить владельцу |

Отчёт владельцу по шаблону:

```
Сделано: <кратко>
Проверки: <итог одной строкой; упавшие с выводом>
Проверить владельцу: <что и как | нет>
Не проверено, риски: <список | нет>
Отступления: <из лога | нет>
Вопросы: <из лога | нет>
Лог: <путь>
```
